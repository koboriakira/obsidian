# obsidian-classify — Obsidian ノート分類スキル

ユーザーが「このメモをどこに置けばいい？」と聞いてきたとき、または新しいメモを作成する際に、
PARA メソッドに基づいて格納場所を提案する。

> **PARA の思想・原則・ノートのライフサイクルは `/para` スキルを参照すること。**
> このスキルは「どこに置くか」の判断ロジックに特化する。

## Vault ディレクトリ構造

```
00_Inbox/       ← 未処理・判断保留
10_Projects/    ← プロジェクト（目標・期限あり、完了できる）
  {プロジェクト名}/
    {プロジェクト名}.md   ← 概要ノート（status フロントマターあり）
    {タスク名}.md         ← タスク・参考情報（混在OK）
20_Areas/       ← 継続的な責任ドメイン（終わりがない）
  {ドメイン名}/
30_Resources/   ← 参照・資料・記録・アイデア（トピック別）
  {トピック名}/
40_Archives/    ← 完了・非活性になったもの
```

## 分類フロー（この順序で検討する）

### Step 1: Projects になりえるか？

以下をすべて満たせば **10_Projects/**:
- **完了条件がある**（「〇〇が終わったら完了」と言える）
- 複数のアクションが必要

> ⚠️ 「終わりがない」だけでは Areas ではない。**完了条件があるかどうか**が判断軸。
> sandpiper のような継続プロダクトは Area（プロダクト維持責任） + Project（個別タスク）に分ける。

**→ すぐ着手できそうであれば、プロジェクト作成も提案すること**

プロジェクトフォルダの作成手順:
1. `10_Projects/{プロジェクト名}/` フォルダを作成
2. `{プロジェクト名}.md` を概要ノートとして作成（フロントマター: `status`, `start_date`, `tags`）
3. **タスクは概要ノート内の `## 次のアクション` チェックリストで管理する（タスクごとに個別ファイルを作らない）**
4. 参考情報・調査メモは追加ノートとして同フォルダに作成してよい

> ⚠️ PARA は知識の外部リソースであり、タスク管理システムではない。タスクの詳細管理は `tasks.md`（Obsidian）で行う。

### Step 2: Areas になりえるか？

以下を満たせば **20_Areas/**:
- 終わりのない継続的な責任・役割
- 一定の基準を維持するもの

例: 家計管理・健康・育児・ベース練習・ポーカースキル向上

**必ずエリア名のサブフォルダを作ってから、その中にノートを入れる:**

サブフォルダ名は仕事・プライベートを区別するため `w_` / `p_` プレフィックスをつける:
```
20_Areas/
  w_チームマネジメント/
  w_キャリア/
  p_育児/
  p_ベース/
  p_投資・資産/
```

### Step 3: それ以外は Resources

**30_Resources/** はデフォルトの格納先:
- 参照資料（技術メモ・書籍ノート・調査まとめ）
- 記録・ログ（観戦記録・支出分析・練習記録）
- アイデア・考察（アウトプット志向でなくてもOK）

**必ずトピック名のサブフォルダを作ってから、その中にノートを入れる:**
```
30_Resources/
  プロレス観戦/
    観戦記録_2026-03.md
    選手メモ.md
  ポーカーGTO/
    プリフロップ戦略.md
```

**サブフォルダ名（トピック名）の決め方:**
- 広すぎるテーマを避ける（「趣味」より「クラフトビール」、「投資」より「株式自動取引」）
- 知的好奇心を刺激する具体的なテーマ、または将来リサーチが必要になりそうなもの
- 詳細は `/para` スキルの「Resources のトピック命名原則」を参照

### Step 4: 判断できなければ Inbox

**00_Inbox/** に一時保管。Arika のコメント・分析・次のアクション候補を含める。

## Archives への移動・ノートの移動

ノートは状況に応じて自由に移動する。詳細な移動パターンは `/para` スキルを参照。

### 移動すべき対象（簡易チェック）

| 種類 | 移動条件 |
|------|---------|
| Projects | status が Done / Trash になった |
| Areas | そのドメインへの責任がなくなった |
| Resources | 参照しなくなった・情報が古くなった |

### Archive への移動方法

- フォルダごと `40_Archives/{元カテゴリ}/` に移動
- 完了プロジェクトのノートを Resources に「昇格」してから Archive することも可
- アーカイブ後は Bases ビューから自動的に除外される

## DB_ ディレクトリへの昇格基準

**原則: まず PARA の分類（どのカテゴリか）を考える。データベース管理が必要かどうかはその後で判断する。**

PARA での配置が決まったあと、以下に該当したら `DB_{Name}/` への昇格を提案:
- Bases でフィルタ・ソートしたくなった（複数プロパティで管理したい）
- ノート数が増えてフロントマターによる整理が必要になった
- 一覧ビューで全体を把握したくなった

## プロジェクト概要ノートのフロントマター

```yaml
---
status: ToDo   # ToDo / InProgress / Done / Suspend / Trash
start_date: YYYY-MM-DD
end_date:
tags: []
---
```

## 分類の返し方

1. どこに置くか + 理由を1〜2行で説明
2. Projects の場合、すぐ着手できそうなら「プロジェクトを作りますか？」と提案
3. サブフォルダ名（トピック名）も提案する
