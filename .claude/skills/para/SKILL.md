# PARA メソッド — 思想と原則

## Atomic ノート原則（最重要）

**1ノート = 1アイデア・1トピック。**

- ノートは再利用可能な最小単位で作成する
- 複数のテーマをひとつのファイルにまとめない
- **迷ったら新規作成する**。既存ファイルへの追記は、そのファイルと同一テーマのときだけ

### 新規作成 vs 追記の判断

| 状況 | 判断 |
|------|------|
| 同じトピックの続き・補足 | 既存ファイルに追記 |
| 別の切り口・別のアイデア | **新規作成** |
| 「どちらか迷う」 | **新規作成** |
| 既存ファイルが長くなりすぎている | **新規作成して分割** |

### なぜ Atomic か

- ひとつのノートが別のプロジェクト・コンテキストで再利用できる
- 検索・参照・引用が容易になる
- 「大きなノート = 良いノート」ではない

Tiago Forte が提唱するナレッジ管理システム。
**ノートは静的な保管庫ではなく、プロジェクトの進行に合わせて動き続けるもの**という思想が核心。

## プロジェクトフォルダの構成

プロジェクト開始時のファイル作成・README.md のエグゼクティブサマリー管理・tasks.md の運用ルールは `/obsidian-project` スキルに従う。

## 4カテゴリの定義

| カテゴリ | 定義 | 特徴 |
|---------|------|------|
| **Projects** | 明確な完了条件を持つ具体的な作業 | 完了できる。終わったら Archives へ |
| **Areas** | 一定の基準を維持し続ける責任領域 | 終わりがない。基準・指針をノートに記録 |
| **Resources** | 将来役立つかもしれないトピック・参照情報 | 興味や参照価値があれば残す |
| **Archive** | 非活性になった上記3カテゴリのもの | 削除せず保管。検索で復活できる |

## Areas と Projects の使い分け（重要）

**「終わりがない = Area」ではなく「完了条件があるか」で判断する。**

### 継続的なプロダクト・サービスの扱い

開発は「手段」であり「目的」ではない。**開発リポジトリの格納先 = そのプロダクトが何を達成しようとしているかの Area**。

| プロダクト | 目的 | 格納先 |
|-----------|------|-------|
| us-jp-sector-leadlag | 投資・資産管理 | `p_マネー/` |
| sandpiper | タスク管理ツール（汎用） | `w_個人開発/`（目的が汎用的な場合の例外） |
| mojizukan | 語学学習支援 | 語学系 Area があればそこ |

開発活動そのものが Area になることはなく、**プロダクトが何のためにあるかのドメインに属する**。

具体的な開発作業は粒度を分ける:
```
20_Areas/p_マネー/
  us-jp-sector-leadlag の維持方針.md   ← Area（責任）

10_Projects/
  us-jp-sector-leadlag_バックテスト改善/  ← Project（完了条件あり）
```

### Areas と目標の関係

Areas は「達成する目標」ではなく「維持する基準を持つ責任」。
ただし、基準・指針をノートとして記録しておくことで目標的な問いと接続できる:

```
20_Areas/p_健康/
  健康の基準.md   ← 「週3回運動」「体重〇〇kg維持」などの指針
  運動ログ.md
```

## ノートのライフサイクル

```
00_Inbox
   ↓ 処理・分類
   ├→ 10_Projects/{プロジェクト}/  ← 今すぐ使う
   ├→ 20_Areas/{ドメイン}/         ← 継続的に管理
   └→ 30_Resources/{トピック}/     ← 将来参照

完了・変化のタイミング
   ├→ 40_Archives/                 ← 非活性に
   └→ 別カテゴリへ移動             ← 状況変化に応じて
```

## ノート移動の原則（PARA の本質）

**ノートは状況に応じて自由に移動させる。**
カテゴリは「保管場所」ではなく「現在の文脈」を示すもの。

### プロジェクト完了・中断時の整理

プロジェクトフォルダ内のノートを性質に応じて振り分ける:

```
10_Projects/ランドセル購入計画/ （完了）
  ランドセル購入計画.md  →  40_Archives/10_Projects/ランドセル購入計画/
  選び方メモ.md          →  30_Resources/育児/ （将来また使えるかも）
  あらたの希望カラー.md  →  40_Archives/10_Projects/ランドセル購入計画/
```

パターン:
- **プロジェクト固有の情報**（決定事項・経緯） → Archives
- **汎用的に使える知識・資料** → Resources の適切なトピックへ
- **フォルダごとまとめてArchive** も許容（中身を仕分けなくてもよい）

### Resources から Projects への引き上げ

参照資料が「今すぐ取り組む作業」になったとき:

```
30_Resources/家計/支出分析テンプレート.md
   ↓ 「今月の家計を見直す」プロジェクト開始
10_Projects/2026-03_家計見直し/支出分析テンプレート.md  （コピーまたは移動）
```

### Areas と Resources の行き来

- Areas のドメインへの責任がなくなる → Resources またはArchives へ
- Resources のトピックが継続的な責任になる → Areas へ昇格

## Resources のトピック命名原則

### 広すぎるテーマを避ける

| NG（広すぎる） | OK（具体的） |
|---------------|-------------|
| お酒 | クラフトビール |
| 健康 | 栄養学 |
| 投資 | 株式自動取引 |
| 趣味 | ベース演奏 |

### 命名の基準

以下のいずれかに該当するテーマで切り出す:
- **知的好奇心を刺激するもの**: 自分が自然と調べたくなるトピック
- **将来リサーチが必要になりそうなもの**: 今は薄くても、深掘りの予感があるテーマ
- **実用的な参照情報**: 繰り返し使う可能性があるもの（例: クリスマスプレゼント、旅行計画）

### テーマの粒度感

- 1つのトピックに 5〜50 ノート程度が収まる粒度が目安
- 広すぎたら後から分割、狭すぎたら統合 — 最初から完璧にしなくてよい

## 中間アウトプット（IP）の考え方

Resources には、ノートから抽出された**再利用可能な中間アウトプット（Intellectual Property）**も保存する。

**IP の例:**
- 複数ソースから抽出した重要な洞察をまとめたノート
- 繰り返し使えるテンプレート・フォーマット
- 半分完成した考察・アイデアの断片
- あとで別プロジェクトに転用できる調査結果

```
30_Resources/株式自動取引/
  Python自動取引ツール開発マニュアル.md   ← 参照資料
  バックテスト設計パターン.md             ← IP（複数試行から抽出）
  使えるライブラリ比較.md                 ← IP（将来のプロジェクトで再利用）
```

**IP を意識した命名・構成のポイント:**
- 「このトピックのノートから何を再利用するか」を想定してフォルダ名を決める
- 将来のプロジェクトがこの Resources フォルダを参照したとき、すぐ使えるような粒度で保存する

## アーカイブの思想

**削除しない。アーカイブする。**

- 情報の価値は「今」だけでなく「将来」にもある
- Archives は検索できるゴミ箱ではなく、休眠中の知識の倉庫
- `40_Archives/{元カテゴリ}/` の構造を維持することで、元の文脈が残る

## 定期レビュー

**週次または月次**で以下を確認:
1. 00_Inbox が空になっているか
2. 完了・中断したプロジェクトはないか → Archives へ
3. 参照しなくなった Resources はないか → Archives へ
4. Archives から復活させたいものはないか
